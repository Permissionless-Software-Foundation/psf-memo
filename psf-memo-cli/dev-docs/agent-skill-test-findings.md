## F1 — Skill documents the wrong repo path

**Severity:** Medium (blocks copy/paste onboarding)

The skill says the CLI lives at `~/psf-memo/psf-memo-cli` and gives an alias:

```sh
memo() { node ~/psf-memo/psf-memo-cli/psf-memo-cli.js "$@"; }
```

On this machine the checkout is at **`~/repos/psf-memo/psf-memo-cli`**, so the
alias fails:

```
Error: Cannot find module '/home/block/psf-memo/psf-memo-cli/psf-memo-cli.js'
```

**Expected:** a path that works, or a note that the location is checkout-dependent.
**Actual:** hard-coded `~/psf-memo`, which does not exist here.

The published file is generated by `blippost.com/scripts/sync-skills.js`, which
rewrites the local path to `~/psf-memo`. The rewrite is fine, but the resulting
`~/psf-memo` assumes a specific checkout. Consider making it generic, e.g.:
"clone `psf-memo` and run from its `psf-memo-cli/` directory".

## F2 — `--json` is NOT implemented on `wallet-*`, `send-*`, `msg-*`

**Severity:** High (contradicts an explicit, bolded claim in the skill)

The skill states, under "Output contract":

> `--json` is implemented on **every** command, including `wallet-*`, `send-*`,
> and `msg-*`.

In practice these commands reject the flag (exit code 2):

```sh
node psf-memo-cli.js wallet-create -n w --json   # error: unknown option '--json'
node psf-memo-cli.js wallet-list --json          # error: unknown option '--json'
node psf-memo-cli.js wallet-addrs -n w --json    # error: unknown option '--json'
node psf-memo-cli.js wallet-balance -n w --json  # error: unknown option '--json'
```

Same for `wallet-sweep`, `send-bch`, `send-tokens`, `msg-sign`, `msg-verify`.

**Cause:** in `psf-memo-cli.js`, the `wallet-create`, `wallet-list`,
`wallet-addrs`, `wallet-balance`, `wallet-sweep`, `send-*-`, and `msg-*` command
definitions never call `.option('--json', ...)`. Every `memo-*` command does.

**Impact:** documented output shapes the skill promises cannot be obtained:

- `wallet-create --json` → `{ name, description, cashAddress, slpAddress, legacyAddress }`
- `wallet-list --json` → `{ wallets: [{ name, description }] }`
- `wallet-addrs --json` → `{ name, cashAddress, slpAddress, legacyAddress }`
- `wallet-balance --json` → `{ name, address, bchBalance, tokens }`
- `wallet-sweep` / `send-bch` / `send-tokens` → `{ txid, explorerUrl }`
- `msg-sign` → `{ address, message, signature }`
- `msg-verify` → `{ address, message, valid }`

**Fix:** add `.option('--json', ...)` to those 9 command definitions and honour it
in the corresponding `src/commands/*.js` (several, e.g. `wallet-balance.js`,
already import JSON helpers — the wiring just stops at the CLI layer).

## F3 — Wallet banner is printed to stdout and corrupts `--json`

**Severity:** High (breaks machine parsing on every wallet-using command)

Any command that initializes the BCH wallet prints this line **to stdout**,
*before* the JSON object:

```
Initializing minimal-slp-wallet routers with this interface: consumer-api
{"message":"address: bitcoincash:...","address":"..."}
```

Repro:

```sh
node psf-memo-cli.js memo-identity -n block --json 2>/dev/null
# stdout (2 lines):
# Initializing minimal-slp-wallet routers with this interface: consumer-api
# {"message":"address: ...", ...}
```

**Expected (per the skill's Output contract):** with `--json`, "exactly one JSON
object to stdout"; diagnostics never go to stdout.
**Actual:** two lines on stdout. `... --json | jq` and `JSON.parse(stdout)` both
fail.

Affects every wallet-backed command, including `memo-follow`, `memo-reply`,
`memo-post`, `memo-name`, `file-host`, etc. (Observed on `memo-identity`,
`memo-follow`, `memo-reply`.)

**Fix:** route the wallet/router banner to stderr (or suppress it entirely when
`--json` is set).

## F4 — `npm install` fails on a fresh machine (unreachable private registry)

**Severity:** High (blocks setup on any machine that isn't on the PSF network)

`package-lock.json` pins the `bch-token-sweep@2.2.1` tarball to a private
registry that is not reachable here:

```
npm error network request to http://94.130.170.209:4873/bch-token-sweep/-/bch-token-sweep-2.2.1.tgz failed,
npm error reason: connect ETIMEDOUT 94.130.170.209:4873
```

The identical version **and integrity hash** is available on the public
registry:

```
https://registry.npmjs.org/bch-token-sweep/-/bch-token-sweep-2.2.1.tgz
sha512-f4UGEpPXzea7HQMRSEb6h/amXiwrlsMBAjl1dVYg5//26IDWeG+e3qVNtMJhm00NMZ0BS+LasUa2xlz0UVziZA==
```

**Workaround used:** change that one `resolved` URL in `package-lock.json` to the
npmjs URL, run `npm install`, then restore the lock file.

**Fix:** repoint the lockfile entry (or the `.npmrc`/publish config) to the public
registry.

## F5 — `wallet-list` emits a raw shell error when no wallets exist

**Severity:** Low (cosmetic; first-run experience)

With no `.wallets/` directory present:

```
ls: no such file or directory: /home/block/repos/psf-memo/psf-memo-cli/src/commands/../../.wallets/*.json
No wallets found.
┌───┬───┐
│ Name │ Description │
└───┴───┘
```

The `ls: ...` line leaks an implementation detail (`shelljs ls` with an
unguarded glob). **Expected:** a clean "No wallets found." **Fix:** guard the glob
or catch the missing directory.

## F6 — `SKILL.md` is missing from the `psf-memo` repository

**Severity:** Medium (the published skill cannot be regenerated from a fresh checkout)

`blippost.com/scripts/sync-skills.js` builds `public/skills/psf-memo-cli.md`
from:

```js
src: path.join(psfMemoDir, 'psf-memo-cli/SKILL.md')   // PSF_MEMO_DIR default: /home/trout/work/psf/code/psf-memo
```

But `psf-memo-cli/SKILL.md` is **not tracked** in `psf-memo` (checked
`origin/master` and full history — no `SKILL.md` anywhere), and the default
`PSF_MEMO_DIR` points at an old developer machine
(`/home/trout/work/psf/code/psf-memo`).

**Impact:** the website's skill file is effectively an orphaned copy; edits
cannot be round-tripped from source, and `npm run sync-skills` fails on a fresh
checkout.

**Fix:** commit `SKILL.md` into `psf-memo/psf-memo-cli/`, and make the sync
script's default path portable (or require `PSF_MEMO_DIR`).

## F7 — Post length wording is inconsistent

**Severity:** Low (documentation)

The skill says a post is **217 UTF-16 code units** and a reply is **184 UTF-8
bytes**; `llms.txt` says a post holds "up to **217 characters**". For non-BMP
emoji these differ. Align the wording (and state which limit applies where).

## F8 — Default `MEMO_DB_URL` points at a stale legacy endpoint

**Severity:** High (all default reads were ~370 blocks ≈ 2.6 days behind)
**Status:** 🟡 workaround (`--db-url https://api.blippost.com` / `MEMO_DB_URL`)

The CLI's production default is `https://memo-api.fullstackcash.net`
(`DEFAULT_MEMO_DB_URL` in `src/lib/memo-db.js`, echoed in the skill's Environment
table). That deployment is **stale**:

```json
// https://memo-api.fullstackcash.net/level/status/status
{"startBlockHeight":524999,"syncedBlockHeight":972255,"chainBlockHeight":972255}
```

The current production endpoint is **`https://api.blippost.com`**, which is
caught up to the chain tip:

```json
// https://api.blippost.com/level/status/status
{"startBlockHeight":524999,"syncedBlockHeight":972621,"chainBlockHeight":972621}
```

(`972621` == `https://bch.fullstack.cash/v6/full-node/blockchain/getBlockCount`
at the same time.)

**Impact:** with the default, nothing written in the last ~2.6 days is readable —
including the follow/reply made during this test — so `memo-wait`, the Following
feed, and thread reads silently miss recent data. Point the client at
`api.blippost.com` and everything works.

**Fix:** change `DEFAULT_MEMO_DB_URL` to `https://api.blippost.com` and update
the skill's Environment table. (`memo-api.fullstackcash.net` should be retired or
redirected.)

## Agent endpoint guidance (confirmed 2026-10-12)

Chris's recommendation checks out. For agent checks, prefer these over
`bch.loping.net`:

| Need | Endpoint | Verified |
|---|---|---|
| Chain tip / block height | `GET https://bch.fullstack.cash/v6/full-node/blockchain/getBlockCount` | ✅ returned `972621` |
| Tx status (confirmations, block) | `GET https://bch.fullstack.cash/v6/full-node/rawtransactions/getRawTransaction/<txid>?verbose=true` | ✅ both test txs → `confirmations: 1` |
| Is a tx still in the mempool? | `GET https://bch.fullstack.cash/v6/full-node/blockchain/getMempoolEntry/<txid>` | ✅ `{"error":"Transaction not in mempool"}` once mined |
| Wallet ops + tx data | `POST https://free-bch.fullstack.cash/bch/txData` with `{"txids":["<txid>"]}` | ✅ `confirmations`, `height`, `blockhash` |
| Wallet backend used by the CLI | `https://free-bch.fullstack.cash` (`/bch/balance`, `/bch/utxos`, `/bch/broadcast`) | ✅ (this is `WALLET_URL`) |

- `free-bch.fullstack.cash` is the `ipfs-bch-wallet-consumer` proxy (wallet +
  `/bch/txData`); it has **no** block-height endpoint, so use `bch.fullstack.cash`
  for the tip.
- `bch.loping.net` (the CLI's printed `explorerUrl`) is **not** reliable for API
  calls: it is fronted by an anti-bot page (Anubis) that returns HTTP 200 with
  HTML, not a tx. Do not treat its 200 as confirmation.
